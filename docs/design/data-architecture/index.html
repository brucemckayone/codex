Should Codex move reads to D1?

A decision document. The problems that prompted the question, what actually causes them, and the changes that fix them — three that matter, none of which is D1.
Why most of this is not about D1: that answer is stable — no amount of growth makes a static binding dynamic or a nullable column a tenant key. Everything else here gets worse with traffic you are about to have.

2026-08-30 · verified against origin/dev · diagrams · plan · evidence

  1. No D1, no per-tenant Durable Objects, no separate read plane. Two facts settle it: D1 bindings are static — there is no runtime addressing — and a Durable Object is a single instance in a single location. Neither is something a bigger plan changes. And the two constraints you framed the question around both dissolve: the 10 GB limit never comes up (the catalogue is 36.6 MB), and sharding was never the risk — the schema has no key to shard on. content.organizationId is nullable and mediaItems has no organisation column at all, so “design to avoid sharding” was designing around a constraint that does not exist in that form. Multi-org queries are not something to preserve through a migration; they are what a migration would have cost you. The model is read from the schema in §2.
  2. Your instinct about cost was right, and for a sharper reason than a per-query price. Neon bills time awake, not queries — and the free monthly compute allowance is only 0.55–0.60× what one minimum-size instance costs to stay awake for a month. (100 CU-hours published, 110 as the quota CI cited, against 182.5 for 0.25 CU × 730 h — the range is immaterial; being under 1.0 is the point) The plan is built for a database that sleeps. You have consumed all of it with one test user, because anything touching the database more often than its idle timeout stops it sleeping — and every request for a real page currently does, paying a Neon round trip just to resolve its slug. The invoice is £0 only because you have not launched. And do not count on the quota resetting to clear the CI block: the usage counter decomposes into the recorded 89.4/10.6 production/CI split to eight seconds and its value scales with the project's age, both signatures of a lifetime figure — though Neon's published pricing says the free allowance is monthly. §5 reading 3 argues both and names the one command that settles it.
  3. So the fix is to stop waking it, and that is not a datastore choice. Four round trips do not need to happen: a driver setting, a missing argument, a missing header, and an unset config key. D1 would inherit every one of them. The single biggest lever is the missing header — it lets Cloudflare's CDN answer anonymous and bot traffic without waking Neon at all. And the diagnosis is confirmed by Neon's own counters: this period recorded zero bytes written. The workload is reads, and all three changes reduce reads reaching the database. None of them touches a write path — which is also why none of them can lose data. The target state is drawn in one table: the architecture — two layers change, both plumbing, and the largest row in it is what is not there.

SECTION 2 Why not D1 — and why the 10 GB limit never comes up

You asked specifically about the 10 GB per-database limit and designing to avoid sharding. That constraint never binds. The whole catalogue is 36.6 MB against 500 MB on D1's free plan — thirteen times over, and 10 GB on the paid one is not in sight. The design fails on how you address a tenant's database, long before how much fits in it.

The tenancy model, since you asked for it — read from the schema, not from docs

RelationHow it is storedWhat it implies
person → org
twice		 organizationMemberships (organizationId + userId) and organizationFollowers (same pair). Note organizationMemberships lives in schema/content.ts, not organizations.ts — a file-wide grep for organizationId misleads. Many-to-many, twice over. A person belongs to orgs and follows others, so any one library view spans an arbitrary set of tenants. This is the relation that makes a database-per-tenant expensive rather than merely awkward.
content → owner content.creatorId is not null; content.organizationId is nullable and references organizations.id. The creator is the owner; the org is optional. Personal-studio content has no organisation at all. So the tenant key you would partition on is absent on exactly the rows people most expect to be isolated.
media → owner mediaItems.creatorId only — no organizationId at any point. Media is creator-scoped, full stop. A per-org store would have to invent an ownership relation that the schema does not have.

And the direct answer to “keep multi-org content queries available”: they stay available because nothing moves. Every cross-tenant query — a library spanning followed orgs, a creator's work across their studios, an admin view over all of it — remains a single SQL statement against one database, with foreign keys and a transaction boundary. That is not a benefit this document engineers; it is the thing a read plane would have taken away, and the reason “avoid sharding” turned out to be the wrong thing to design for. Sharding was never the risk — the schema has no key to shard on.

Two reasons settle it

ReasonWhy it is decisive
D1 bindings are static. There is no runtime addressing — you declare one binding per database in configuration, at deploy time. This kills per-tenant D1 outright. The only shape that works is N declared bindings: one config entry plus a redeploy to onboard anybody, against a ~5,000-binding ceiling. That is a fixed roster, not a multi-tenant architecture. workerd issue #3564 — one reply since February 2025.
A Durable Object is one instance in one location. It cannot be replicated. This kills the per-tenant Durable Object alternative. A distant reader still crosses the network to reach that one instance — so you reintroduce exactly the round trip the whole exercise exists to remove.

Between them those two rule out both versions of the proposal — a database per org, and a Durable Object per org. Everything below is corroboration; you do not need it to reach the answer.

Why none of this is a budget question

Only one objection anywhere in the case against D1 is about a plan limit — free-tier D1 being 500 MB with 50 queries per invocation. Every other reason holds on any paid plan, because static bindings, a nullable column, a many-to-many relationship and SQLite's own parser limits are not things money changes. Someone who wanted D1 could buy past the plan limit and still meet all six of the others.

SECTION 3 The fixes

Three changes fix problems 1–4, and they are ordered by effect on the thing that is actually breaking — how often the database is woken. A fourth closes the search question. Two more are conditional and may never be worth doing. None is architectural, and four of the six have a working precedent in this repo — you are not designing anything new. Two bounded sweeps of origin/dev are worth stating up front, because they change what these fixes are: of the eight workers, only two have public routes at all, and content-api carries 13 cache-header references to organization-api's zero; of the six files doing fire-and-forget writes, five thread waitUntil correctly. So this is not a platform that fails to cache, nor a team unaware of the waitUntil trap — it is two specific files that missed a pattern applied correctly everywhere else. Both defect classes are closed by fixes 1 and 2; there is no third instance waiting to be found. But “precedent” is not “paste”, and each size below was revised after opening the file that hosts the change. Two of my four original estimates were wrong, both optimistic, and both for the same reason: I had sized the logic and forgotten the plumbing. Fix 2's waitUntil is not in scope where the write happens; fix 3's Hyperdrive binding does not exist in any worker yet. Neither is visible when you look at the defect — which is why the sizes here are stated per file rather than per idea.

The one thing not on this list, and why it is not — recurrence

Both defect classes above are closed by fixes 1 and 2. Nothing prevents them coming back. The reference document carries a seventh action for that — make the omission unconstructable rather than merely documented, by splitting the cache-write type so a caller cannot build one without supplying a waitUntil. It touches 40 construction sites across 24 production files (85 across 34 counting tests).

Left off deliberately, and the reasoning is worth having: it fixes no current bug, and it is larger than every fix above it. But it is the only item that addresses why these two defects existed at all. The negative cache for unknown subdomains was built carefully, bounded, and documented — while the same write on the path carrying all the traffic went unwrapped, and its test passes either way. Five of six files thread waitUntil correctly, which means the pattern is understood and simply not enforced.

So: not now, but do not lose it. The cheap version is a lint rule or a required parameter on one type; the thorough version is the type split. Either way it belongs after fixes 1–3, when you know what the corrected shape looks like — enforcing a pattern before you have settled it is how a convention becomes a constraint you fight.

What fix 3 should buy you — and why the 81 ms is the interesting number

Same-region network round-trip time is ~5–10 ms. So the 81 ms per statement is not distance — it is HTTP and TLS setup, paid fresh for every statement, because neon-http opens a new connection each time. That is exactly what a connection pool removes.

The floor is therefore set by RTT, not by 81 ms — and query caching removes eligible repeat reads from the database entirely. I am deliberately not quoting a post-fix total: it depends on how many of the ~31 statements are cacheable, and that has not been measured. Measure it rather than predict it.

What to record before and after, so the change is attributable: p50 and p95 for one logged-out landing render, the statement count for that render, and the 504 rate. The same-region figure is the control — if it does not move, the cost was never handshake and something else is going on.

Fix 1, in full — the pattern already in the repo

Quoted from workers/content-api/src/routes/public.ts:67-70 so you do not have to go and find it. The comment above it in that file is worth reading too: the 60 s window is a deliberate choice, not a default.

app.use('*', async (c, next) => {
  await next();
  c.header('Cache-Control', 'public, max-age=60, s-maxage=60');
});

Three lines, mounted before the routes. The existing comment explains the reasoning to inherit: “set to 60 s (s-maxage=60 for CDN) so edge drift stays bounded now that the KV layer has working event-driven invalidation. A longer window would let CDN-cached responses serve stale content up to max-age after publish, defeating the invalidation.”

Two things to get right when copying it into organization-api. First, app.use('*', …) applies to every route on that router — content-api can do that because its public.ts holds only public routes. And this too is the whole of its defect class — a sweep of all eight workers on origin/dev found only two with public routes at all: content-api has 3 and 13 cache-header references; organization-api has 5 and zero. The other six declare no auth: 'none' route, so there is nothing to cache and nothing to fix. And apps/web's SSR layer already has its own discipline — lib/server/cache.ts exports a CACHE_HEADERS table with deliberate presets (max-age=0, s-maxage=300, stale-while-revalidate=3600 for pages that are personalised for signed-in visitors but cacheable for anonymous ones), applied across dozens of +page.server.ts files. So the gap is one worker, not a platform-wide habit. It is not the same, and this is the one thing to get right today: organization-api/src/routes/organizations.ts holds 13 procedure() routes of which only 5 are auth: 'none'. A blanket app.use('*') there would stamp Cache-Control: public on eight authenticated responses — a data-exposure bug, not a caching bug. So scope the middleware to the five public paths, or mount it on a sub-router that holds only those. content-api can use the wildcard because its public.ts is public-only; that is a property of the file, not of the pattern. Second, the negative control already exists in content-api's test — expect(res.headers.get( 'Cache-Control') ?? '').not.toContain('public') on an authenticated route. Copy that assertion too; it is the one that would catch the mistake above.

Three behaviours to know before starting fix 3 — all invisible locally

Every hazard in this change shares one property: the environment convenient to test in omits exactly the machinery whose behaviour is the risk. Query caching, the read-after-write window, and the double-pooling trap above are all absent under wrangler dev — so a green local suite is not weak evidence here, it is no evidence. This is the same shape as fix 2, where a mock records a call and only the real runtime cancels it. Both defects live in what the platform does after your code returns, which is the one thing a local harness cannot simulate.

BehaviourWhat to do
Hyperdrive caches read queries by default — 60 s max_age plus 15 s stale_while_revalidate, so the real staleness window is 75 s, and there is no purge on write. Create a second, cache-disabled config and route auth, sessions, permissions, billing and post-write reads through it:
wrangler hyperdrive create <name> --connection-string=… --caching-disabled
It still gets pooling. Account for total origin connections across both configs — Neon allows 839 here, so this is comfortable. Diagnose staleness via the cacheStatus metric: hit / miss / disabled / uncacheable.
Since 2026-02-23 Hyperdrive refuses to cache queries containing PostgreSQL STABLE functions — NOW(), CURRENT_TIMESTAMP, CURRENT_DATE — matched as text, so even the name in a comment counts. This codebase trips it in exactly one place: access/src/services/content-access/library.ts:706. It is the library read path — the hottest query here and so the one that most wants caching. One-line fix: compute the timestamp in the worker and bind it as $1.
Neither pooling nor query caching runs under wrangler dev. A green local run is not evidence for fix 3. Verify with --remote or in a deployed environment. The read-after-write bug this could introduce cannot appear locally, because the cache is not there.

What can these changes break? Staleness and latency — not data All three touch how reads are served, never how writes happen: a response header, an argument to waitUntil, and which driver opens the connection. Neon's counters record zero bytes written this period, so there is no write path in play to get wrong. The realistic failure modes, in order of likelihood: a public page shows content up to 60 s old (fix 1 — choose the max-age deliberately); a stale read after a write, which is why fix 3 needs a second --caching-disabled Hyperdrive config for auth, sessions, permissions and billing; and a burst of KV 429s in the first second after fix 2, which is expected rather than a fault. Each is reversible by reverting one line. None can corrupt a row.
And if you do nothing? It gets worse on its own Not "stays as it is". Every one of these costs scales with traffic, and you have almost none yet. The database is awake 5.2% of the time for one test user; each new visitor adds ~31 statements and holds the compute awake through all of them. The allowance is already spent at this volume. What breaks first, in order: the compute allowance again, within days of real traffic rather than months; then p95 on public pages, because 31 sequential round trips at 81 ms do not degrade gracefully — they hit the 504 you already see 17% of the time under load; then the KV write budget, since the org cache still writes on every request and never lands. The one thing that does not get worse is the D1 question — see the masthead for why. Which is exactly why this document is short about it and long about everything else.
