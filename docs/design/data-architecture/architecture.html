SECTION 1How it works today

One page render, end to end. The shape that matters is on the right: every SQL statement opens its own HTTPS connection to the database.

The parts, and which are load-bearing

LayerWhat it does todayState
Cloudflare CDN Would serve public pages from the edge — but organization-api sends no Cache-Control, so every anonymous visitor reaches a worker. inert
Worker SSR and API. Resolves the org from the hostname, checks access, renders. ~31 SQL statements for a landing page. works, but chatty
KV cache Two write-throughs — org slug→id and membership. Both call kv.put(...) without passing it to waitUntil, so the platform cancels the write when the response returns. 0% hit rate
Driver drizzle-orm/neon-http — one HTTPS request per statement. No pooling, no reuse. the root cost
Neon System of record. All 48 domain tables, one region, transactions and foreign keys intact. Nothing wrong with it. healthy
Durable Objects Two, both correct: auth rate limiting keyed on the email being tried, and an alarm-driven orphaned-file cleanup. healthy

SECTION 2What is wrong

Three caches sit between a visitor and the database. All three are open. Not misconfigured — absent, cancelled, and never built.

Why this shows up as a bill rather than as slowness

Neon charges for the time the compute is awake, not for queries. A render that holds it awake for 2.5 seconds costs 2.5 seconds of compute — and the free allowance is 0.55–0.60× what one minimum-size instance costs to stay awake for a month. The free tier is a bet that your database sleeps.

That allowance has been consumed at a traffic level of roughly one test user. The database is awake 38 hours a month — 5.2% — and the branch archived on 2026-08-30 after 24 hours with no caller at all. So the 5.2% is not a low steady load with room to grow. It is bursts separated by silence, and launch traffic removes the silence.

SECTION 3Why not D1

The proposal was a database per organisation. The schema has no line you can draw to separate them.

Two facts settle it before capacity is ever reached

FactConsequenceBuyable?
D1 bindings are static. There is no runtime addressing — you declare one binding per database in configuration, at deploy time. Per-tenant means one config entry plus a redeploy to onboard anybody, against a ~5,000-binding ceiling. A fixed roster, not a multi-tenant architecture. No
A Durable Object is one instance in one location. It cannot be replicated. A distant reader still crosses the network to reach it — so the per-tenant DO alternative reintroduces exactly the round trip the exercise exists to remove. No
Free-plan D1 is 500 MB with 50 queries per invocation. The only objection money reaches — and the catalogue is 36.6 MB, so the 10 GB limit never comes up. Yes

Two layers, both plumbing. The data model, the transaction boundaries and the multi-tenant query paths are untouched.

SECTION 5The likely outcome

The honest version: two effects are near-certain, one is measurable-not-predictable, and one thing does not improve at all.

OutcomeConfidenceWhy
Anonymous page loads stop reaching the database. near-certain A CDN cache hit does not invoke a worker. The only question is the max-age you choose, and content-api has already chosen 60 s for the same kind of content.
The compute sleeps far more often. near-certain Neon archives a branch untouched for 24 hours — so you can watch this happen for free by reading current_state before and after.
Per-render latency drops substantially. measurable,
not predictable		 Same-region RTT is 5–10 ms against 81 ms per statement, so the handshake is ~90% of it. Record p50, p95, statement count and 504 rate before you start — the same reading also replaces the six figures in this document that come from four-day-old measurements.
The compute-quota problem goes away. likely, with a caveat 89% of consumption is production traffic, which these fixes reduce. But whether the free allowance is monthly or a spent grant is unresolved — one command after 2026-09-01 settles it, and the prudent assumption is that you pay.
Cross-region reads get faster. not addressed Nothing above shortens a transatlantic round trip. Every latency figure in this document is a European measurement. Fix 5 (placement) is the cheap first answer if the traffic reading says it matters — one line per config, currently unset in all eleven.
Data is at risk. no All three changes touch how reads are served — a response header, an argument, a driver. Neon's counters record zero bytes written this period; there is no write path in play. Worst case is a page 60 seconds stale, reversible by reverting one line.

What to do first, and what it depends on

Fixes 1 and 2 can be written and verified today, while CI is still red — both of their test files mock @codex/database, so neither needs a Neon branch. They are also the two biggest levers on how often the database wakes.

Everything after that waits on two readings: cpu_used_sec after 2026-09-01, which decides how urgent the Neon plan is; and the colo distribution in the Workers logs, which decides whether fix 5 is worth doing at all. Both are one command; the second needs a Cloudflare token with account:read.
