Implementation plan — a data-access contract, then the fixes as instances of it

The six changes in the decision are point repairs. This plan makes them consequences of a rule that applies to every worker, every route and both access layers — so the next one is correct by construction rather than by review.

SECTION 1Why a contract, not six fixes

The diagnosis found organization-api missing a cache header. The reason it was missing is more interesting than the omission: there was no rule to violate.

There are two data-access layers, and they do not share a vocabulary

The pattern this repeats, and why enforcement is the answer

The same shape appeared three times in the diagnosis. Five of six files thread waitUntil correctly and one does not. Content-api sets cache headers in thirteen places and organization-api in none. The negative cache for unknown subdomains was built carefully, bounded, and documented — while the identical write on the path carrying all the traffic went unwrapped.

In every case the knowledge existed in the codebase and did not reach the next file. A convention that lives in a comment, a docstring or one team member's habit reaches exactly as far as the last person who read it. The fix is not more documentation — it is to make the declaration mandatory at a point every route already passes through.

The two properties that make this a contract rather than a table

1 · The default is the safest cell, not the most useful one. Declaring nothing must yield private — the same way procedure() already defaults auth to 'required' and rateLimit to 'api'. A forgotten declaration then costs a cache hit, never a leak.

2 · One vocabulary, both layers. The presets move to @codex/constants so a worker and a SvelteKit load can name the same thing. Today they cannot, which is why one says 300 seconds and the other 60 for arguably the same content — and neither is wrong, because there was nothing to be wrong about.

SECTION 3Where it is enforced

The enforcement point already exists and 199 routes already pass through it. procedure() declares auth, roles, org membership and rate limiting. Caching is the missing member of that set, not a new mechanism.

What the declaration looks like

// today — caching is invisible, and nothing notices
procedure({
  policy: { auth: 'none' },
  input:  { query: publicContentSchema },
}, async (ctx) => { … })

// with the contract — one line, and three things follow from it
procedure({
  policy: { auth: 'none', cache: 'public' },   // ← the whole declaration
  input:  { query: publicContentSchema },
}, async (ctx) => { … })
//   ⇒ procedure() sets Cache-Control from the named preset
//   ⇒ ctx.db is the CACHED Hyperdrive client
//   ⇒ ctx.cacheWrite() threads waitUntil for you — the org-helpers defect
//      becomes unconstructable rather than merely fixed

Why this is the right place, in the codebase's own terms

procedure() is already the answer to this question for three other concerns. Auth is not a convention developers remember — it is policy.auth, defaulting to 'required'. Rate limiting is not a habit — it is policy.rateLimit, defaulting to 'api'. Both default to the safe value, both are declared at the route, both are applied by one piece of machinery.

Caching is the same kind of concern and is currently handled the other way — by a middleware in one worker, by hand in ten files, and not at all in five routes. Adding it to the policy is not a new pattern; it is finishing an existing one.

What is deliberately not a work package

Parallelising the access-check ladder. access-decision.ts has 13 awaited checks and one Promise.all — and the sequential ones short-circuit, so parallelising trades "sometimes one query" for "always four". Someone already made that trade for the pair where it pays and declined it for the rest. It is worth even less once WP5 lands and round trips are cheap.

Anything that moves data. No second datastore, no projection, no read replica, no sharding. Which is also why the 59 test files that need a database need no structural change — and why none of these packages can lose data: all eight touch how reads are served, and Neon's counters record zero bytes written this period.

How this changes the answer to “how do I add a route?”

Today: read the surrounding file, notice whether it sets cache headers, guess whether yours should, and hope the reviewer knows. That is how five public routes ended up with no header while three in another worker had thirteen references to one.

After: answer one question — who may see this response? — and declare it. The cache policy, the database binding and the write-through behaviour follow from that single word, and the wrong combinations do not compile.

The test of whether this worked is not that the six defects are fixed. It is that a year from now a new worker with public routes is cached correctly by someone who never read this document. That is the difference between a plan and a system.

Sequence. WP1–2 are additive and change no behaviour. WP3 and WP4 can be written and verified today, while CI is red — both of their test files mock @codex/database. WP5 waits on the $5 decision and a deployment; WP6 on a working database; WP7 follows WP1; WP8 on the traffic reading. The checks in §5 land with the WP that makes each one satisfiable, not at the end.
