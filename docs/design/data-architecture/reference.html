On the premise — “the cost is rather high for frequent queries”

That sentence is why this investigation happened, so it deserves a direct answer. The Neon compute invoice is £0. The project is on the free tier, and it consumes 9.9 CU-hours a month — awake 5.2% of wall-clock, at an average 0.258 CU, sitting at the lowest minimum Neon offers. What is actually biting is the free compute quota, not a bill — cpu_used_sec reads 396,646 against a 396,000 allowance, which is why CI has been failing at Create Neon branch rather than anywhere in the application. The distinction matters because the two have different remedies. A high bill argues for cheaper storage — which is the D1 hypothesis, and §03 says no. A blown quota argues for using less compute time, or for paying. And the split settles which: of the 396,646 project compute seconds, 354,610 (89.4%) are the production branch and 42,036 (10.6%) are deleted CI branches — the same 89/11 split on active time. So the quota is driven by production traffic, not by CI, and the §05 actions are exactly what reduces it: less time awake per request is less compute consumed. A first draft of this paragraph said “a substantial share of the consumption is CI”. That was wrong — 10.6% — and it was asserted from the fact that CI branches exist rather than from the two numbers, which were already in hand. The correction runs in the plan's favour: had CI been the bulk, none of §05 would have addressed the quota. So the honest reframing: the actions in §05 are worth doing for the measured 17% 504 rate and the request latency behind it. They are not a cost programme, because there is no cost to remove — and the thing that is failing today is a compute quota driven 89% by production traffic — which §05 does reduce — with the $5 plan as the immediate unblock. None of this was visible until the compute reading was taken, which is the one thing this document deferred to for its whole life and which took one command (§07.1).

On the question as asked — the 10 GB multi-tenancy limit

The question that started this named D1's 10 GB per-database limit as the constraint to design around: how to avoid sharding while keeping cross-org queries available. That limit never binds, and the reason is worth stating before anything else: the design fails on addressing long before it fails on capacity. A per-tenant database cannot be selected at request time at all (D1 bindings are static, §03), and content.organizationId is nullable — so there is no per-org partition to size in the first place. Sizing was never reached. And the figure itself is wrong for this account: 10 GB is the Workers Paid ceiling; on the free plan — which two wrangler.jsonc comments confirm is where this platform sits (§05.4) — a D1 database caps at 500 MB, twenty times smaller, with 50 queries per invocation rather than 1,000. Any sizing done against 10 GB would have been off by a factor of twenty. So the sharding question (§A8) has an answer, and it is that there is no ceiling to shard against — not because the catalogue is small, but because the partitioning it would shard was never available.

02.3 · Hazard classes, abstracted from the individual defects

The hazard classes, stated once

  1. A swallowed error on a shared quota is a silent outage. This is the meta-cause: Codex-kgrdp.11 states that “this epic exists because a resource ran down invisibly” — nothing reports KV op volume, and VersionedCache, kv-secondary-storage, cacheSessionInKV and RateLimiter all catch-and-continue. “Correct for availability; catastrophic for diagnosis.” Graceful degradation without a signal is indistinguishable from working. It is why this document found three separately-valid explanations for one 0% hit rate: none of them reported anything, so all three fitted the evidence. Pair every swallowed error on a shared, exhaustible resource with a log-once and a budget alarm — and prove the alarm fires, per .11's acceptance test.
  2. Never write unconditionally, per request, to a quota-capped shared store. The failure is not local — it exhausts a budget every other consumer depends on, and it fails silently and elsewhere. Two instances here: the rate limiter (.3) and version-key minting for attacker-chosen slugs (Defect 2, since fixed).
  3. Client identity is only trustworthy at the entry worker. Where workers call workers, CF-Connecting-IP on the inner worker is the caller's Cloudflare egress address, not the user's. Codex-kgrdp.16 proves it with production analytics: 34% of all zone traffic, and 78% of auth traffic, came from a single address in Cloudflare's own egress range — including the window's only real sign-in. So any per-client control must sit at the entry point (or the WAF), or the identity must be explicitly forwarded. .17's “key on subject (email), not IP” is the same lesson applied.
  4. On per-operation-billed infrastructure, “cheap” must mean operations, not milliseconds. .6's in-code comment — “Cheap: 3-4 parallel KV reads (~10ms)” — judged latency, which was fair, and ignored billed operations, which is what ran out. Every performance comment on a serverless path should state which metric it means.

02.4 · What the closed bead says — and one alternative ruled out

The most important line in the closed bead

Codex-e32xz's close reason ends: “STILL UNVERIFIED: that the production hit rate actually rises — in-process Miniflare does not cancel the floating put the way deployed workerd does, so confirm with wrangler kv key list after deploy.”

The mechanism is fixed but the outcome is unconfirmed, and the fix is two days old. We do not currently know what Neon load looks like with a working cache. That single fact is why §05 is structured around a measurement gate rather than a migration plan.

Worth crediting — and a warning for this proposal

The bead records that the original diagnosis was correct but incomplete in three ways: getWithResult() held a byte-identical copy of the same defect; warmTierCache was a false reassurance (it wrapped an IIFE in waitUntil, but cache.get resolved before its own put); and a second latent defect was masked — public.ts built a PaginatedResult inside the cache fetcher, so a cache hit round-tripped through JSON and failed procedure()'s instanceof check, degrading the list envelope. Landing the cache fix alone would have broken GET /api/content/public on the first hit.

The lesson transfers directly: a read plane will surface latent bugs that only appear on a cache hit — every read-plane row crosses a serialisation boundary. the appendix's shadow-projection step (§A6) exists for exactly that reason.

Ruled out: “just add indexes” is not a cheaper answer — the catalogue is already indexed

Before accepting the driver diagnosis I checked whether the hot queries simply lack indexes, which would be a far cheaper fix. They do not. content carries the right composites:

So every public read path is index-backed except search. That independently corroborates .23's central claim — “IT IS TOO MANY QUERIES, NOT SLOW QUERIES” — and it makes action 9 surgical rather than speculative: title/description are the only unindexed public columns.

One procedural friction with action 9. There are currently no CREATE EXTENSION, GIN, trigram or tsvector statements in any migration — pg_trgm would be the first extension this schema uses. And one failure mode worth knowing before you write it, from Neon's own troubleshooting: “permission denied to create extension” is raised when the database was created via direct SQL rather than the Neon Console or API — such databases lack the privileges the operation needs, and the fix is to grant all privileges on the database to neon_superuser. Since this would be the schema's first extension, that permission has never been exercised here, so it is untested rather than known-good. Check it on a branch first — one statement, and it either works or names its own remedy. But not today: creating a Neon branch is exactly what the exhausted compute quota is currently refusing (§05.0 step 0a — cpu_used_sec 396,646 against 396,000, which is why CI fails at Create Neon branch). So this action's cheapest verification is blocked by the same quota that blocks CI, and both clear on 2026-09-01. Worth knowing before someone spends an afternoon wondering why the test will not run. Also settled while checking: Neon documents both gist_trgm_ops and gin_trgm_ops. GIN is the right one here for a reason worth stating rather than assuming: it gives faster lookups at the cost of slower writes and a larger index, and content rows are written once and searched repeatedly. GiST would be the choice if the indexed columns churned. The GIN index itself is expressible in Drizzle (.using('gin', …) with an opclass), but CREATE EXTENSION is not, so it needs a hand-written migration — which cuts against the project's own rule (generate migrations, never hand-write SQL). Treat it as a deliberate, documented exception of two statements, not a precedent.

02.5 · The studio population, and what action 5 must exclude

The larger 504 population resolves to action 4 — the studio design does not need changing

.23 DEFECT 4 puts 741 studio 504s at LHR — the owner's own session, and the bigger of the two populations. The mechanism is the SPA fan-out: the studio is ssr = false, so one mount fires several concurrent _app/remote/* queries. Counted on studio/+page.svelte, the dashboard alone calls five — getActivityFeed, getDashboardStats, getOrgMembers, listActiveAgreements, listPendingProposals — which matches the endpoints the bead names as 504-ing.

Each is a separate worker invocation that re-pays the procedure() policy tax — slug → orgId plus a membership check — on top of its own query. At .23's measured ~2 queries/request that is roughly 10 Neon queries per dashboard mount, and more on heavier pages. So ssr = false converts what would be one server render (one invocation, one policy resolution, queries batchable) into N invocations, each paying the fixed cost again.

But the conclusion is not “abandon the SPA”. Both halves of the policy tax are supposed to be cached, and Defects 6a/6b are why they are not. Once action 4 lands the tax becomes 2 KV reads instead of 2 Neon queries, and a five-way fan-out is cheap. The studio 504s are largely a symptom of the broken caches, amplified by a design choice that is otherwise sound — ssr = false buys instant navigation, and CLAUDE.md documents that trade deliberately. Fix the caches; keep the architecture.

And what action 5 must not include — .4 defers itself

Codex-kgrdp.4 (“VersionedCache costs 2 KV reads on every cache HIT, by design”) looks like it belongs in this action. It does not. The bead carries its own sequencing note: “currently MOOT and must not be worked before Codex-kgrdp.2. So the read-per-hit question is undecidable until action 4 lands and hits exist. That is the same discipline this document applies to the gate, applied by the bead to itself — and it is why the version-key work in 5b is limited to .6's collapse (4 reads → 1, which holds regardless of hit rate) and excludes .4's optimisation (which depends entirely on a hit rate nobody has yet).

It also corrects something I dismissed. I rejected per-request memoisation as low-yield, citing .23's 1.87 Neon queries/request. .4 is pointing at a different quantity: “N lookups currently pay N version reads for a value that cannot change mid-request.” That is genuine intra-request duplication — of KV version reads, where several entities resolved in one request each re-read a version that is immutable for that request's lifetime. Memoisation is the right tool there; I waved it off with the wrong number.

Action 6 · DRIVER, specified — and “Hyperdrive or plain pg” was a false choice

I have written “Hyperdrive or plain pg” as though interchangeable. They are not. Action 9 · TRGM, specified — two statements, and the caveat that decides whether it works

Search is or(ilike(title, '%q%'), ilike(description, '%q%')). Verified at source, and one trap. The predicate is exactly that, at two call sites — content-service.ts:1009 and :1177 — with % and _ escaped, so the pattern is always a literal substring: precisely what a trigram index serves. The trap: the second arm reads ilike(content.description ?? '', …), and that ?? '' is a no-op — content.description is a column object, always truthy, so it never fires. Harmless today (SQL NULL ILIKE '%…%' correctly does not match), but it looks like a NULL guard. If someone “fixes” it to coalesce(description, '') in SQL, the GIN index on that column stops being usable and search silently returns to a sequential scan — the same invisible-regression shape as everything else in this document. A B-tree cannot serve a leading wildcard; a trigram GIN index can. Neon's docs are explicit that pg_trgm “also helps regular expression-based searches, such as with LIKE and ILIKE”. 

-- one hand-written migration (this schema's first extension)
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_content_title_trgm
  ON content USING GIN (title gin_trgm_ops);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_content_description_trgm
  ON content USING GIN (description gin_trgm_ops);

Two indexes, not one: the query is an OR across two columns, which the planner serves with a BitmapOr over both. gin_trgm_ops lowercases during trigram extraction, so it covers ILIKE without a separate lower() expression index. CONCURRENTLY avoids taking a write lock — worth it even on a small table, since it costs nothing here.

The caveat that decides whether it works: trigram indexes need at least 3 characters in the pattern, so a 1–2 character search still falls back to a sequential scan. Enforcing a minimum is the right answer — a one-character search over a catalogue is not a useful query — but not as a local .min(3). Running the wider grep in §07.0 gives 12 declarations of search: z.string() across 9 files — content-schemas.ts (×4), plus admin-schemas.ts, category-schemas.ts, schemas/access.ts, schemas/subscription.ts, and four *.remote.ts files. Not one has a minimum. An earlier revision of this document said “five”, having grepped only two files. Patching one leaves eleven scan paths open.

Define it once instead: a searchTermSchema = z.string().min(3).max(255) primitive in packages/validation/src/primitives.ts — which already houses createSlugSchema — used at all five sites. That is the same move as action 8 (TYPESPLIT): one definition, no drift. That is hazard class 5 in §02: a rule that must hold at N call sites needs one enforcement point, not N correct authors.

Two procedural notes. The GIN indexes are declarable in Drizzle (index('…').using('gin', sql`${table.title} gin_trgm_ops`)), but CREATE EXTENSION is not — so this needs a hand-written migration, against the project's own generate-never-hand-write rule. Treat it as a documented two-statement exception. And the acceptance test is EXPLAIN ANALYZE showing a Bitmap Index Scan rather than a Seq Scan (§05.2) — not a stopwatch, which at this data volume would show no difference either way.

Two things the migration as written gets wrong.

1 · CONCURRENTLY will fail here. It cannot run inside a transaction block, and although scripts/migrate-direct.ts issues no explicit BEGIN, it sends the whole migration file as one query string (await client.query(migration.sql) at :111). PostgreSQL's simple query protocol executes multiple statements in one message inside an implicit transaction — so CONCURRENTLY is exactly as unavailable as if the transaction were explicit. Drop it. On a catalogue this size a plain CREATE INDEX completes in milliseconds and the brief write lock on content is not worth a second mechanism. Reinstate CONCURRENTLY only once the table is large enough to matter, and then as its own single-statement migration.

2 · .min(3) is a breaking change, and the wrong place to enforce it. A 1–2 character search is a legal request today — the schema is z.string().max(255).optional() with no minimum — so adding a server-side minimum turns working requests into 400s. Better: gate it in the client (SearchPill already debounces; it should simply not issue a request below three characters — no error, no wasted round trip, no regression), and keep searchTermSchema's minimum as defence-in-depth for direct API callers. Then the trigram index applies to every query that reaches Postgres, and nothing that works today stops working.

Action 8 · TYPESPLIT, specified — use the compiler as the census

Verified on origin/dev, 2026-08-30: new VersionedCache appears 85 times across 34 files (an earlier revision of this document said “32 sites”, which was low). Roughly half have waitUntil within three lines of the construction.

That proxy is crude in a way that makes the argument rather than weakening it. A read-only cache use legitimately omits waitUntil; a write-through must not. A mechanical count cannot distinguish “needs it and lacks it” from “correctly omits it” — and neither can a reviewer reading a diff. If a grep cannot tell, the type system should. That is the whole case: not that 85 sites are wrong, but that no cheap audit can establish which ones are.

This is the recommendation I would defend hardest and had specified least. Two constraints shape it: Biome here runs only recommended, noExplicitAny and useConst, and Biome has a fixed rule set — so the custom lint rule earlier revisions proposed is not available. That is fortunate, because the type system is the better mechanism: make waitUntil required and tsc enumerates every site exactly, where three regex passes gave three different answers.

A blanket requirement would be wrong, though — many call sites only invalidate, and (an earlier revision said “21 of 32”; that ratio was computed against the wrong denominator — the real total is 85 across 34 files, and the invalidate-only share is unverified. The split matters, the ratio is not yet known.) invalidate() awaits its write internally. So split the type by capability, and the defect becomes unconstructable rather than discouraged:

A worked example arrived from this document's own tooling, which is why this action is stated as an invariant rather than a convention. The consistency checker had a documented hazard — “split at the §07.1 HEADING, not the first textual mention: the table of contents repeats section titles ~150 KB earlier” — written as a comment beside the one check that handled it. A later check was then written using free-text lookup anyway, and broke within the hour: the moment a new section was given a TOC entry, the marker matched the contents page and the check measured the wrong table. Three remedies were available and only the third worked. An audit found the existing sites but stopped no new ones. A documented convention did not survive an hour against its own author. Removing the shape — no free-text variant left in the file at all — did. And it happened four times in this tooling, independently, which is what turns an anecdote into evidence: free-text markers became element ids everywhere (three recurrences before the shape was removed); a cwd-relative path became process.chdir(git rev-parse --show-toplevel) after a verifier silently reported FAILS on a load-bearing proof; a keyword-anchored CSS grep became a whole-rule match after a truncated read led to corrupting the stylesheet; and an ad-hoc negative test became a harness assertion s != before after a probe that matched nothing reported success. In every one the documented convention existed first and did not hold. What held was removing the wrong option. And they share something more than the remedy: every one failed silently and plausibly. A wrong-table count returns a number. A cwd-dependent grep returns empty. A truncated rule reads as complete. A no-op mutation reports a pass. None threw; none looked wrong — which is precisely why a convention could not save them, because there was nothing to notice. That is the argument for making waitUntil a required constructor argument rather than a documented rule: omitting it does not error either. It produces a cache that never hits — four times, in a codebase whose own comment reads “the fix is waitUntil, not await”. That is the whole argument for this action, observed rather than reasoned: a rule that must hold in N places, where a wrong version is still expressible, degrades to a rule that holds wherever someone last remembered it.

And there is a stronger version of the argument, visible only once the whole codebase had been read: the discipline here was already good, and it still did not transfer between files. Five of the ten hazard classes in §02.3 were already written down — kv-budget.ts states class 1 verbatim, limits.ts:25 states class 3 with its remedy shipped, procedure() handles class 10 at two deliberate layers, and class 8 is stated in a test comment on a payment path. Six of nine recommendations in this document turned out already implemented. None of it reached the next file. So this action is not asking anyone to be more careful. It asks for the one thing careful authors demonstrably cannot do: make a rule hold in a file they are not editing. A required constructor argument does that. A comment in the file where the lesson was learned does not, however well written — and several of these were written very well. 

// reads a data slot ⇒ writes one ⇒ waitUntil is REQUIRED
class VersionedCacheReader {
  constructor(cfg: { kv: KVNamespace; waitUntil: (p: Promise<unknown>) => void; prefix?: string });
  get<T>(id, type, fetcher, opts?): Promise<T>;
  getWithResult<T>(…): Promise<CacheResult<T>>;
}

// bumps a version ⇒ awaits its own write ⇒ no waitUntil needed
class VersionedCacheInvalidator {
  constructor(cfg: { kv: KVNamespace; prefix?: string });
  invalidate(id): Promise<void>;
  getVersion(id): Promise<string | null>;
}

// for hand-rolled writes outside the class (org-helpers.ts, Defects 6a/6b)
function kvWriteThrough(args: {
  kv: KVNamespace; key: string; value: string;
  waitUntil: (p: Promise<unknown>) => void;   // required
  expirationTtl?: number;
}): void;

The migration is then mechanical and self-enumerating. Rename the class, and every one of the 85 sites becomes a compile error until it is classified as reader or invalidator. No audit, no worklist, no heuristic — and no way for the next call site to get it wrong. The 5 candidates in the census stop being a guess and become whatever tsc reports.

Backstop for what the types cannot see: a CI grep failing on a bare .put( against a KV namespace outside those three entry points. Crude, but the pattern is already established here — scripts/build.sh and scripts/prep-review.sh both use grep gates — and it catches the hand-rolled case that bypasses the class entirely, which is exactly how Defects 6a and 6b arose.

A reader/invalidator split is the wrong shape — verified, and the better form is smaller.

Six files use VersionedCache for both reading and invalidating: explore/+page.server.ts (8 reads, 1 invalidate), _org/[slug]/+layout.server.ts, content-api/routes/categories.ts, content.ts, journeys-cache.ts, and the implementation itself. Splitting the type by capability would force five real call sites to construct and hold two objects for one cache — friction with no safety benefit, since neither object is the one that can be wrong.

The goal is narrower than the name suggests. It is not “separate reads from writes”; it is make it impossible to construct a cache that write-throughs without a waitUntil. That needs two constructors, not two types: VersionedCache.readOnly({ kv }) for version checks and staleness — which legitimately need no waitUntil and are the majority of the 85 sites — and VersionedCache.withWriteThrough({ kv, waitUntil }) for cache-aside, where the argument is required. The six both-files use the second, which can also read. No call site holds two objects, every write-through path is checked by tsc, and the read-only sites are untouched rather than churned. That is a smaller change than the one this action originally described, and it is the one that actually prevents the defect.

05.4a · Action 5, specified — and a prerequisite that changes its shape

Action 5 has been carried as one line all along — “one Hono middleware on organization-api's public group, the pattern content-api already uses.” That is still the code change. Two facts, verified 2026-08-30

  1. Workers Cache is opt-in, and it is not enabled here. Cloudflare's mechanism for “return cached HTTP responses from your Worker without executing your Worker code” requires [cache] enabled = true in the Worker's config. Checked across every wrangler.jsonc files on origin/dev: the only "enabled": true present is observability.enabled. Every worker also carries "compatibility_date": "2025-01-01", well before this surface was documented. So a Cache-Control header added today reaches browsers — real, and worth having — but does not cause Cloudflare to serve the response without running the Worker. Action 5 needs a config line as well as a middleware.
  2. Once enabled, omitting Cache-Control caches for two hours. Cloudflare applies RFC 9111 heuristic freshness with per-status defaults: 200 → 7200 s (2 hours), 301 → 1200 s, 404 → 180 s. In their words: “Omitting Cache-Control is not the same as opting out of the cache.” To opt out you must return no-store or private explicitly.

The second fact inverts the action's risk profile, and puts it in this document's own hazard catalogue. Read casually, action 5 is a small performance win on five public routes. Read against the default, enabling the cache without a policy on every route is the dangerous half — because a route that says nothing gets two hours, and organization-api's group also serves authenticated traffic. That is hazard class 10's shape exactly: the omission is not neutral, it silently selects the aggressive option. Compare the waitUntil defect, where omitting an argument silently cancels a write, and the KV quota, where exhaustion silently zeroes a cache.

Plan limits They bind sooner, and money fixes them. 500 MB, 50 queries per invocation, 100,000 Hyperdrive queries/day — all free-tier, all lifted by action 3. These are the only limits in this document that growth makes more pressing and that no design change addresses.

So the honest summary of when to re-open this. Not at a user count, not at a row count, and not at a request rate — those either leave the argument untouched or strengthen it. Re-open it if step 3b shows the traffic is concentrated rather than long-tailed, and then only for the concentrated subset. And one caution on that measurement: a mean will always look encouraging, because a few busy tenants pull it up. The distribution is the point — §A5 records that this document's own cache-hit reasoning was wrong until it was framed as P(repeat within TTL) rather than as an average.

A3Durable Objects — per-tenant no; the two already here, yes

To be precise: this rules out per-tenant Durable Objects, not Durable Objects

Two already exist in this repo and both are correct uses:

  • packages/security/src/rate-limit-do.ts, bound in workers/auth — Codex-kgrdp.17's landed design. At current volumes neither is close; the point is that they share it.   • workers/media-api/src/durable-objects/orphaned-file-cleanup-do.ts — scheduled cleanup driven by alarms.

The distinction is what a DO is for. Both of these use it for coordination: serialized state for one subject, or a timer. Duration billing is irrelevant because the object is active only while coordinating. A per-org DO holding tenant data is the opposite shape — it must be warm whenever that tenant is being read, so cost scales with active tenant count, which is the same trap as the Neon bill this proposal set out to reduce. Coordination: yes, and already done. Storage-per-tenant: no.

Down to one optional job. Earlier revisions proposed two (HostRouter + Counter); Codex-kgrdp.17's mechanism analysis removed the first. What remains is a rule about shape.

D1 has no duration charge. DOs bill wall-clock while active at $12.50/M GB-s, and the included 400,000 GB-s ÷ 0.128 GB ≈ 36 days — about one permanently-warm object. So the cost of a DO design is set by how many objects are simultaneously active, for how long:

A5The structural limit of caching

This is the durable argument for D1, and it holds regardless of whether the KV mechanism works. A cache returns an answer you already computed. It cannot answer a question.

Your catalogue cache is already at the edge of what a blob cache can do

The team built a sophisticated per-filter-combo key (public-cache.ts):

The comments show this was hard-won — featured was “the latent bug”, omitted from the key so ?featured=true (Editor's picks) and the unfiltered list shared one slot and served each other's data. That class of bug is inherent to hand-managing a combinatorial key space.

export function shouldCachePublicContentQuery(query) {
  return !query.search && !query.creatorId;   // ← always Neon
}

Search is the sharpest case: uncacheable and unindexed

Of everything in this investigation, this is the clearest structural win. Public search in listPublic is: 

const searchCondition = or(
  ilike(content.title, `%${escaped}%`),
  ilike(content.description ?? '', `%${escaped}%`)
);

A leading-wildcard ILIKE cannot use a B-tree index — it needs a trigram (pg_trgm) or full-text index, and none is evident in the schema. So every public search is a sequential scan of content, on two columns, and the query is explicitly excluded from the cache. It is the most expensive public read shape on the platform, with no mitigation currently available at any layer: the CDN cannot key it usefully, KV refuses it, and Postgres cannot index it as written.

Superseded — read the box below as history, not a recommendation

The argument that follows was this document's last reason to build any part of D1, held across eight revisions. It is wrong. Neon's pg_trgm indexes the same query — its docs state the GIN index “also helps regular expression-based searches, such as with LIKE and ILIKE” — and for the mid-word %term% matching this codebase actually performs, trigrams are the more correct index than FTS5's default tokeniser, in the database that already holds the data. That is action 9, one migration, no second datastore. Everything below about FTS5 is retained only because the reasoning shows why the conclusion changed.

D1 supports FTS5 [verified: d1/sql-api/sql-statements, Apr 21 2026]

D1's supported SQLite extensions include the FTS5 module for full-text search (with fts5vocab), the JSON extension, and math functions. So the read plane turns an unindexed double-ILIKE scan into an indexed MATCH — with ranking, prefix queries and phrase support you do not have today.

This is the one endpoint where the read plane is not merely cheaper but qualitatively better, and it needs no change on the Neon side to obtain.

What D1 changes, restated precisely

D1 replaces N cached answers with one indexed table. Any filter combination, any page depth, and creatorId become a single indexed query against a local read replica; search becomes an FTS5 match. No key space to manage, no warming, no per-colo cold start, no invalidation storm — a publish is one UPSERT, not the eviction of 200 keys. And unlike KV it returns a negative result safely and cheaply.

Note what this argument does not claim. It does not say Neon is too slow, or that Postgres is the wrong engine, or that tenant data belongs elsewhere. It says one narrow thing: combinatorial read shapes are a poor fit for a blob cache and a natural fit for an edge-replicated SQL read model. That is the whole of the case — and it bounds the work to the endpoints that have that shape.

Why space is a generated column, not a written one

The projection would write only organization_id and creator_id, copied verbatim from Neon. space is GENERATED … STORED, so the database derives it and it cannot disagree with its sources — removing a whole class of projection bug, where an org-less row silently lands under the wrong partition. STORED is indexable and costs storage; VIRTUAL would recompute on every read. One caveat from the docs: a column added later via ALTER TABLE ADD COLUMN must be VIRTUAL — so declare this at table creation, not in a migration.

The discovery rule a “pre-joined read model” is most likely to drop

listPublic pushes eq(content.courseOnly, false) for catalogue reads only. The by-slug branch is deliberately exempt, and the comment names the incident it prevents:

“a course-only practice … must never be advertised in a public listing — that is how a paid curriculum came to be listed as free, browsable content (Codex-0biug). The by-slug branch above is deliberately EXEMPT … Excluding it here would turn a correct paywall into a 404 and would break any deep link into a practice.”

Both paths run through the same endpoint (/ with an optional slug), so a read model that flattens them re-opens a known bug — and it fails in the worst direction: paid content becomes publicly browsable, silently, with no error.

Make it structural, not remembered. The DDL defines rm_browse as a view with the predicate baked in. Browse (shapes A/B/C) reads rm_browse; the by-slug detail read uses rm_catalogue. Indexes live on the base table and are used through the view. That way the correct behaviour is the default, rather than a predicate every future query author must remember — which is precisely how it was lost the first time.

The same shape again, in membership — and a pre-existing gap it exposed

…/creators and the public member count both go through one predicate: 

activeCreatorWhere(orgId) =
    organizationId = ?
    AND status = 'active'
    AND role IN ('owner','admin','creator')

Drop status='active' and invited-but-never-joined or suspended-for-cause people appear on a public page as creators of the org. Drop the role list and plain members are promoted to public creators. Same failure direction as Codex-0biug: silent, no error, over-exposure. Hence rm_space_creator — the predicate baked into a view, so browse cannot forget it.

And enumerating the triggers surfaced a gap that already exists. OrganizationService.delete() sets organizations.deletedAt and nothing else — no cascade to content, memberships or courses. listPublic has zero org-deleted guards. So content belonging to a soft-deleted organisation keeps deletedAt = NULL and status = 'published', and /discover — which passes no orgId — will list it. The org's own pages 404; its content stays browsable platform-wide.

Mechanism verified in code on origin/dev; not observed in production, and the severity depends on whether orgs are ever soft-deleted in practice. Worth a bead either way. For the read plane the decision is explicit: org soft-delete must be a re-projection trigger that removes that space's rows — which is the third P-column trigger gap this section has had to name.

A security property that falls out of the design

The read plane holds only publicly-renderable fields. That inverts today's shape: a procedure() handler selects from the full table and must remember to strip what should not be public — the failure mode being an accidental over-select. In the read plane the private columns are not present, so they cannot leak, whatever the query says.

So rm_space_people's column list is an explicit allowlist: username, name, avatar_key, bio, social_links, role, status, joined_at. No email, no auth fields, no Stripe identifiers. user_id is present only as a projection key — and the endpoint doc for …/creators states “No emails or internal user IDs are exposed”, so the response mapper must continue to drop it. Verify that claim against the current serialiser: the query selects users.id, so either it is stripped downstream or the comment is stale.

The read plane is a store, not a response

“Pre-joined read model” actively invites the mistake of returning rows straight to the client. Do not. Two rules in the current code make the boundary explicit, and both must survive:

  • resolveR2Urls(items, env.R2_PUBLIC_URL_BASE) — media keys become URLs per-request, from an env var.
  • resolveCategoryCoverUrl(coverImageKey, r2Base) — “Never expose the raw R2 key — resolve the md variant to a CDN URL.” The /md.webp suffix convention lives in that helper, not in the data.

So: keys in the store, URLs in the response, resolution in the worker. The read plane's job is to make the query fast; the mapping layer stays exactly where it is. This is not a stylistic preference — conflating store shape with response shape is precisely what produced the PaginatedResult-through-JSON bug in Codex-e32xz, where a cache hit failed procedure()'s instanceof check and silently degraded the list envelope.

Column provenance — the rule that governs all five tables

Four successive drafts of this section contained bugs, and all four were the same kind: a column placed in a layer that could not guarantee its correctness. The fix is not more care but a classification. Every column in the read plane must be exactly one of four kinds, and the kind determines what can go wrong with it.

Every P column needs a named trigger — this is the gap the sweep alone will not close

A V column re-projects when its own content row changes, which the existing seam already catches. A P column can go stale when something else changes:

  • duration_secs — when the media item finishes transcoding. Not a content mutation at all; the trigger is in media-api's RunPod webhook.
  • creator_name — when the user renames themselves. The trigger is in identity-service, which today only calls cache.invalidate(userId). Without a hook there, a renamed creator keeps their old name on every public card indefinitely.
  • category_slugs — when a category is renamed or deleted, which is a category mutation, not a content one.
  • title_sort — only when title changes, so the content seam covers it.

Two of these four have no trigger in the current design. Either add hooks at those two seams, or accept a bounded staleness and let the cron sweep repair — but say which, per column, rather than discovering it as a bug report about a stale creator name.

Derive aggregates, never store them — and the creators endpoint proves it

…/creators today costs three Neon queries plus JavaScript stitching: a count(), a memberships ⋈ users ⋈ content group-by for contentCount, then a raw window query for recent items per creator. An earlier draft of this document put published_count and latest_content_id on rm_space_people to serve it. That was wrong twice.

  • Both are maintained aggregates, so both drift on any publish, unpublish or delete — the exact failure the categories model was just redesigned to avoid.
  • The cardinality was wrong. The real query is ROW_NUMBER() OVER (PARTITION BY creator_id ORDER BY published_at DESC) filtered rn <= 4 — the endpoint wants the creator's four most recent items, not one.

Two pieces of good news. That window function runs on SQLite unchanged (window functions are supported), so nothing needs translating. And scoping it by space removes the inArray(creatorId, …) IN-list, which at limit=100 would sit right on D1's 100-bound-parameter ceiling. With rm_cat_a_creator (space, creator_id, published_at DESC) the whole endpoint becomes one index-covered D1 query — replacing three Neon queries and the stitching loop.

Text sorts do not survive a change of engine

discoverContentQuerySchema allows sort ∈ {newest, oldest, title}, and rm_category orders by sort_order, name. Both order on text, and that is not portable: 

Postgres  ORDER BY title   → database collation (e.g. en_US.UTF-8 / ICU)
SQLite    ORDER BY title   → BINARY: byte order, so 'Z' (0x5A) < 'a' (0x61)

  input:  Apple, banana, Cherry
  Postgres → Apple, banana, Cherry
  SQLite   → Apple, Cherry, banana     ← silently different

COLLATE NOCASE is not the fix — it folds ASCII only, so accented titles still diverge. Materialise the sort key in the projection instead, where full Unicode is available (Intl.Collator / toLocaleLowerCase), and order by that column. Note the contrast with space: space is a generated column because string concatenation is deterministic and ASCII-safe, whereas title_sort must be projection-written because SQLite's lower() is ASCII-only. Both choices are about keeping correctness in the layer that can actually guarantee it.

This generalises: every ORDER BY on a text column is a cross-engine hazard, and it fails silently — results are returned, just in the wrong order. §A9's contract tests must assert ordering explicitly, with a non-ASCII fixture.

A6.4 · How the projection would work — it would hook a seam that already exists

This needs no new plumbing. packages/content/src/services/content-invalidation.ts already centralises every content-mutation side-effect, and its signature already carries exactly what a projection needs:

Its callers are already few and already centralised: content-service.ts:553, :775, :834 and admin/content-management-service.ts:202, :291. The projection is a sibling call at the same seam — same trigger points, same background dispatch, no new invocation surface to audit.

One content mutation → one batch()

batch() is a single SQLite transaction: statements commit sequentially and non-concurrently, and any failure aborts and rolls back the whole sequence. So all five tables stay consistent with each other without needing triggers: 

await env.READ_PLANE.batch([
  // 1. the row itself — space is GENERATED, so it cannot drift
  upsertCatalogue,          // INSERT … ON CONFLICT(content_id) DO UPDATE

  // 2. FTS: delete-then-insert, since fts5 has no upsert
  deleteFts,                // DELETE FROM rm_catalogue_fts WHERE content_id = ?
  insertFts,

  // 3. category membership — replace, not append (mirrors syncContentCategories)
  deleteContentCategories,  // DELETE FROM rm_content_category WHERE content_id = ?
  ...insertContentCategories,  // ≤ 100 bound params per statement → chunk

  // 4. unpublish / delete is the SAME path with the row removed
]);

Three constraints this shape respects, each of which would otherwise be a bug:

  • FTS5 has no ON CONFLICT. A plain INSERT on re-projection would silently duplicate the document and corrupt ranking. Delete-then-insert, in the same batch.
  • 100 bound parameters per statement (§A4) — a content row has ~20 columns, so one upsert is safe, but the category inserts and any bulk rebuild must be chunked. The 30-second cap applies to the whole batch, not per statement.
  • Membership is a replace, not an append — exactly what syncContentCategories already does on the Neon side (“Clear current membership first — this is a replace, not an append”). Copying that semantic keeps the two stores' behaviour identical, which is what makes the contract test in §A9 meaningful.

A6.5 · What it would delete

The read plane is a net reduction in moving parts — the main reason to prefer it over any alternative in §06.

  • The per-filter-combo key machinery. public-cache.ts — buildPublicContentCacheType, shouldCachePublicContentQuery, getCachedPublicContent — exists only to hand-manage a combinatorial key space. Four indexes replace it, and so does the bug class it produced (the featured collision).
  • The MAX_LIBRARY_FANOUT workaround, for catalogue reads. content-invalidation.ts fans a version bump out to every user holding an item, with a hard cap — above which it silently skips and relies on the client's visibilitychange. That cap exists because a blob cache cannot express “invalidate everything derived from this content”. A projection is one UPSERT; every reader sees it, with no fanout and no cap.
  • Defect 4, for the five migrated endpoints. Once they no longer read KV, the shared-version-key over-invalidation stops applying to them.
  • The getBySlug fallback in the org layout, once L1 answers space existence authoritatively.

The simplification test

A proposal that only adds is usually the wrong shape. This one adds five derived tables, two guard views and one FTS5 index, plus a single projection call, and removes a combinatorial cache-key builder, a capped fanout workaround, and a duplicate org lookup. If the deletions in 7.5 do not actually happen, the design has been implemented wrongly — the read plane is meant to replace the caching machinery for those five endpoints, not sit in front of it.

A8Avoiding sharding

The direct answer first: the requirement is met by not partitioning at all

The brief asked to “design in a way that avoids sharding while keeping multi-org content queries available”. That requirement is satisfied by the recommendation, not by anything below:

  • There is no 10 GB ceiling to shard against. The limit that motivated the concern is D1's, per database. Neon has no per-tenant ceiling; storage scales as one database and is billed by the gigabyte, not capped. The constraint only exists in the design being rejected.
  • Multi-org content queries stay single statements — verified, not assumed. library.ts:586-589 and :730-733 build the multi-org filter as managementOrgIds.map((id) => sql`${id}`) — an inlined IN (…) list inside one statement, with managementOrgIds collected once at :188. No loop, no per-org query. That shape is only possible because every organization's content shares one database. Partition it and the same question becomes an N-way fan-out against a 6-connection-per-invocation cap — §03's proof 3, since user↔org is many-to-many twice. Worse, it would break on D1 a second, independent way: D1 caps bound parameters at 100 per query, so even the single-statement form fails for a user in 100+ organizations. Postgres has no comparable practical limit. Two unrelated D1 constraints, one query.
  • The shard key already exists if it is ever needed. space = organizationId ?? 'creator:' + creatorId is defined and used in the codebase today. It makes every row's partition key non-null, so a future move is a mechanical change rather than a schema redesign. Nothing needs it now — and article bodies (content.contentBody, inline text) would be the first thing to move out if size ever became the binding constraint, which is the same policy the read-plane discussion below arrives at for a different reason.

Everything below is the contingency answer — how the size ceiling would be bounded if the gate in §05.5 ever opened. Two of its policies are worth knowing regardless, because they apply to any derived store you ever build here: exclude article bodies, and project published non-deleted rows only.

Straightforward here — because the read plane holds derived data, and derived data can be bounded by policy rather than by whatever your tables happen to weigh.

Two policies that bound the size by construction

  • Exclude article bodies. content.contentBody is a plain text column holding article bodies inline (plus contentBodyJson). At 100 k articles × 50 KB that is 5 GB — half the ceiling. A catalogue read model needs title, slug, thumbnail, duration, price, gates, not the body. Serve bodies from Neon or R2 on the detail page.
  • Published, non-deleted rows only. Drafts and soft-deleted rows never enter the read plane — which also dissolves the tension between your never-hard-delete rule and D1's ceiling. Deleting from a projection is not a data-integrity event; the audit trail lives in Neon.

With both, a catalogue row is roughly 1 KB — order-of-millions of published items inside 10 GB (§A7.1). But 10 GB is the Workers Paid ceiling; on the free plan a D1 database caps at 500 MB — 20× smaller, which at 1 KB/row is order-of-hundreds-of-thousands, and this document's measurements all come from the free plan. Any sizing here must state which plan it assumes.

The real ceiling is write throughput

Once size is bounded by policy, the binding constraint becomes single-threaded write concurrency — and the profile is favourable: projections fire on studio authoring (low volume, low concurrency) while reads scale horizontally on free replicas. The Counter DO removes the one pathological write pattern.

Instrument these, not gigabytes

  1. D1 p50/p95 SQL duration — the throughput denominator.
  2. overloaded error rate — queue saturation.
  3. rows_read per request — an unindexed query is invisible until the bill arrives.
  4. Read-model row counts, and size as a % of the ceiling for the plan you are on — 500 MB free, 10 GB paid.
  5. Projection lag — the user-visible staleness budget.

Two decisions that cost nothing now

  1. Key every read-plane row on space (§03) and route every query through one accessor — getReadPlane(space) — from the first commit, even though it returns the same binding for every space. Sharding then becomes a change in one function, and the shard key already exists, is non-null, and covers org-space and creator-space alike.
  2. Never write a read-plane query without space. That is what keeps the shard key usable and mirrors the discipline orgScopedNotDeleted() already enforces.

/discover is the one endpoint that forbids sharding — name it now

Shape C in §03 is unscoped by design: the route comment says “No org scoping — intentionally platform-wide”. A global browse cannot be answered from a space-sharded store without fanning out across every shard, which the 6-connection cap forbids. So:

The half that matters. Cloudflare is explicit: “When using localConnectionString, Hyperdrive's connection pooling and query caching do not take effect. Your Worker connects directly to the database without going through Hyperdrive.” So in wrangler dev:

  • The benefit is invisible. Pooling is the entire point of action 6 — and it is exactly what does not run. A green local suite says nothing about whether the 504s are fixed.
  • The principal risk is also invisible. Query caching is on by default — 60 s max_age plus a 15 s stale_while_revalidate, so the real staleness window is up to 75 s, and no purge on write. Two specifics read 2026-08-30: max_age can be raised to 1 hour; and since 2026-02-23 Hyperdrive treats PostgreSQL STABLE functions as uncacheable — NOW(), CURRENT_TIMESTAMP, CURRENT_DATE — detected by text pattern matching, so the name inside a SQL comment blocks caching for that query too. This codebase has exactly one such site: packages/access/src/services/content-access/library.ts:706, AND ${subscriptions.currentPeriodEnd} > NOW()) — in the library read path, the hottest query here and therefore the one that most wants caching. Cloudflare's own fix is one line: compute the timestamp in the Worker and bind it as $1. An earlier draft of this document counted “59 INTERVAL/NOW() rewrites” as a cost of moving to D1; re-counted against origin/dev, the figure for application query code is one — the rest are migration files and JavaScript identifiers (ink-renderer.ts alone has twelve INTERVAL constants in a shader). New surface — build it with the projection, not after

  1. Projection contract tests. Mutate in Neon → run the projection → assert the read model matches. Three assertions carry disproportionate weight:
    • Space normalisation — an org-less content row must land under 'creator:'||creator_id, an org row under its organization_id. This one assertion protects the whole partitioning scheme.
    • Ordering, with a non-ASCII fixture — ORDER BY on text is a silent cross-engine hazard (§A6.3). Include titles differing only by case and by diacritic; assert the exact sequence, not set membership.
    • Course-only rows are invisible to browse but readable by slug — the Codex-0biug regression, in both directions. Assert a course_only row is absent from every browse shape and present on its by-slug read. This is the one contract test whose failure is a paywall bypass rather than a cosmetic bug.
    • Membership status and role guards — a status='invited' and a role='member' row must be absent from …/creators. Second instance of the same over-exposure shape as the course-only rule.
    • Re-projection idempotence — project the same row twice and assert one row in rm_catalogue and one document in FTS5. FTS5 has no ON CONFLICT, so a missing delete duplicates the document and corrupts ranking without erroring.

  3. wrangler d1 migrations apply in deploy. Per feedback_seed_scripts_must_be_in_deploy, deploy runs only db:migrate — a D1 step that exists only locally will silently skip in production.
  4. Local dev via Miniflare with --persist-to ../../.wrangler/state so it shares state with the existing workers. The pattern exists — dev-cdn uses Miniflare R2.
